| Time | Commit | Description |

The session started from a Cloudflare D1 dashboard showing 21–53 M **rows read**
per query against a catalog of ~28 k objects and, by the user's account, very
little user traffic. Three separate causes, found in that order.

---

## The metric that misleads

**D1 bills rows the engine *visits*, not rows returned.** Every diagnosis below
turns on that. A `LIMIT 50` query that scans 28 k rows to find its 50 bills 28 k.
The dashboard's `Rows read / rows returned` column is therefore the most
useful one on the page: a ratio near 1 is an index seek, a ratio in the
thousands is a scan wearing a `LIMIT`.

Two false leads worth recording, because both looked convincing:

1. **User traffic.** The `TLE_LINE1` queries have `Count` in the thousands,
   which reads like page loads. They are not — they are `buildGroupArtifacts()`,
   21 bundles rebuilt 4×/day by the ingest. Query `Count` in that dashboard is
   executions, and an ingest run executes a lot of them.
2. **`ingest_runs.d1_requests`.** The admin dashboard's `D1` column counts
   **HTTP round trips** to the D1 API ([`env-node.mjs:151`](../../workers/orbit-ingest/scripts/env-node.mjs#L151)),
   each of which can carry many semicolon-joined statements. It is not rows and
   not statements. `b28e3d14` made this column go **up** (the 8/25 18:41 run
   reported 1107, the table's highest) while genuinely reducing cost, because
   the fix adds one cheap `SELECT` round trip per 40-row batch. **Do not judge a
   rows-read fix by that column.**

## 1 — `OFFSET` paging was quadratic (the big one)

[`pagedRows()`](../../workers/orbit-ingest/src/derive.js#L455) walked every
catalog-wide read with `LIMIT 1000 OFFSET n`. SQLite cannot seek to an offset —
it reads and discards every row before it — so page *k* re-walks the entire
prefix. Over 27 k live objects in 1 k pages that is `Σ 1000k ≈ n²/2P`.

Measured on a real engine (`node:sqlite`, the same schema), not reasoned about:

| Rows | Page | OFFSET visits | Keyset visits | Ratio |
|---|---|---|---|---|
| 1,000 | 1,000 | 2,000 | 1,000 | 2.0× |
| 5,000 | 1,000 | 20,000 | 5,000 | 4.0× |
| **27,000** | **1,000** | **405,000** | **27,000** | **15.0×** |

405 k rows visited to return 27 k. That is the `1.05M` rows-read line at the top
of the dashboard, and it applied to **every group bundle *and* the full catalog**,
4×/day.

Fixed by keyset pagination — `WHERE … AND NORAD_CAT_ID > ? ORDER BY NORAD_CAT_ID
LIMIT 1000`, carrying the last row's id forward as the cursor. `NORAD_CAT_ID` is
`INTEGER PRIMARY KEY` (a rowid alias), so each page is a direct seek.

`pagedRows()`'s signature changed from `(db, sql)` to
`(db, {select, from, where, params})`. That is not cosmetic: the cursor must be
ANDed **into** the `WHERE`, before `ORDER BY`, so it cannot be appended to a
finished SQL string the way the old `LIMIT/OFFSET` suffix was.

### The trap this fix nearly walked into

`e19c9516` (earlier the same day) forced `INDEXED BY idx_objects_name` on 8
groups, and its commit message warns that a **mixed predicate demotes a forced
index from SEARCH to a full SCAN** — which is why `stations` and `military`
deliberately carry no hint.

`AND NORAD_CAT_ID > ?` is exactly such a predicate. Adding it could silently
have undone the previous fix while every test stayed green, because the existing
EXPLAIN QUERY PLAN test built its SQL from `where` alone and never saw the
cursor.

The test now takes a `cursor` flag and the plan assertion runs **with** the
cursor clause present, so it checks the shape the Worker actually executes.
All 8 hinted groups still report `SEARCH objects USING INDEX idx_objects_name`.
The two fixes compose — but that was verified, not assumed.

## 2 — `/api/decay-watch` full-scanned the decay table

Worst ratio in the dashboard: **53.67 M rows read, 10.63 k rows read per row
returned**, on 376 calls.

The endpoint resolved "latest message per object" with

```sql
JOIN (SELECT NORAD_CAT_ID, MAX(MSG_EPOCH) AS latest
      FROM decay GROUP BY NORAD_CAT_ID) latest ON …
```

Correct, and unusable: SQLite's planner cannot turn a `GROUP BY … MAX()` over a
whole table into an index walk, so every call scanned all of `decay` — which by
[its own schema comment](../../d1/orbit.sql#L155) holds Space-Track's *historical*
messages back to Sputnik 1, not just live predictions.

Rewritten as a correlated `NOT EXISTS` ("no later message exists for this
NORAD"), which SQLite answers by walking the existing
`PRIMARY KEY (NORAD_CAT_ID, MSG_EPOCH)` index. `MSG_EPOCH` sorts lexically the
same as chronologically (fixed-width upstream format), so `>` is valid on the
raw text.

Semantics are unchanged and the existing test *"the latest message per object
wins, not the first"* still passes — that test is the guard here, and it already
existed.

## 3 — The `b28e3d14` read that is *not* a problem

`upsertObjects()` now issues one
`SELECT NORAD_CAT_ID, GP_ID FROM objects WHERE NORAD_CAT_ID IN (…40 ids…)` per
batch, ~700 per GP run. Flagged as a suspect during the session and cleared:
`NORAD_CAT_ID` is `INTEGER PRIMARY KEY`, so an `IN` list of 40 is 40 rowid
seeks — ~28 k rows read per run total, against the 405 k the paging bug was
spending. It costs round trips (hence the wall-clock and `d1_requests` rise),
not rows.

## After the fix: what the remaining reads are, and why they are fine

Confirmed live on the manual `gp` run (32873291586). The dashboard's query text
no longer contains `OFFSET` — it now reads `AND NORAD_CAT_ID > -1 … LIMIT ?`,
with a live cursor mid-walk (`> 31285`) on later pages. Whole-run totals dropped
to **316 k rows read**, against the ~405 k the paging bug spent on a *single*
catalog walk. Worst ratio went from **10,630 → 133**.

Every one of the 21 bundle counts is byte-identical to the pre-fix run
(starlink 10973, oneweb 654, active 18593, …), which is the real evidence the
rewrite is semantically neutral on production data.

The two largest remaining reads were investigated rather than assumed:

| Group | Reads | Ratio | Plan | Arithmetic |
|---|---|---|---|---|
| `weather` | 111.88 k | 133 | `SEARCH … USING INDEX idx_objects_type (OBJECT_TYPE=? AND rowid>?)` | 18,585 PAYLOADs × 6 pages ≈ 111.5 k, filtered by 8 name prefixes → 140 hits |
| `fengyun-1c-debris` | 34.45 k | 6 | same, on `DEBRIS` | 10,310 DEBRIS × ~3.3 pages ≈ 34.4 k → 1,963 hits |

Both are **correct**, for three reasons worth recording:

- **The cursor is inside the index seek** (`rowid>?` in the plan), so each page
  starts where the last ended. No prefix re-walk — the pager is working.
- Neither group carries an `indexHint`, correctly: both mix `OBJECT_TYPE` with
  their name/id test, and a forced name index degrades a mixed predicate to a
  full SCAN. `idx_objects_type` is the right index here.
- A ratio of 6 is close to optimal without an index on `OBJECT_ID`.

`weather`'s 133 is the type partition itself, not the pager: 18,585 PAYLOADs
filtered by 8 name prefixes down to 140.

### All 21 groups, measured

The two above were then extended to every group, with a counting UDF over a
seeded 31 k-row catalog rather than a cost model. **The model was wrong twice**,
which is the reason to measure:

| Bucket | Groups | Visited / returned | Status |
|---|---|---|---|
| Name-prefix seek | starlink, oneweb, qianfan, hulianwang, galileo, beidou, irnss, sbas | **2** | optimal — `e19c9516`'s hints |
| Type/country partition | active, geo, weather, resource, gps-ops, iridium-next, glo-ops, 4 debris families | **1–133** | index-optimal |
| No usable index | stations, military, last-30-days | **~31,000** | unfixable, see below |

Two corrections the measurement forced:

- **`active` is ratio 1, not 19.** It visits 18,585 and returns 18,585. The
  first estimate assumed each of its 19 pages re-walks the PAYLOAD partition;
  it does not, because `idx_objects_type` resolves as
  `(OBJECT_TYPE=? AND rowid>?)` — `NORAD_CAT_ID` **is** the rowid, so the keyset
  cursor is pushed into the index seek and the 19 pages make one pass.
- **A `(OBJECT_TYPE, NORAD_CAT_ID)` composite index is ignored by the planner**,
  for the same reason: `idx_objects_type` already supplies that ordering free.
  Proposed, tested, rejected — it would have been pure write cost.

### Why the last three cannot be fixed

`stations`, `military` and `last-30-days` each visit the whole live catalog
(~31 k) regardless of returning 1, 24 and 177 rows. Every candidate fix was
tested and each is **worse**:

| Attempt | Result |
|---|---|
| `military`/`stations` + `INDEXED BY idx_objects_name` | `SCAN objects` + `USE TEMP B-TREE FOR ORDER BY` — strictly worse, and exactly what `e19c9516`'s commit message predicted for a mixed predicate |
| `last-30-days` + a new `LAUNCH_DATE` index | planner ignores it, still picks `idx_objects_decay` |

Their predicates (`OBJECT_NAME IN (24 literals)`, `NORAD_CAT_ID IN (…) OR name
LIKE …`, `LAUNCH_DATE >= date('now', …)`) cannot combine with the mandatory
`DECAY_DATE IS NULL AND TLE_LINE1 IS NOT NULL` through any single index. ~97 k
reads/run is the honest price of three bundles.

**Conclusion: ~316 k rows read per run is near the floor for this schema — for
the group bundles.** The remaining spend there is real work: the `active` bundle
*is* 18.6 k objects, and a ratio-1 read is the definition of the work rather
than waste. Do not re-open the bundle queries without a schema change.

## Exporting the dashboard's query table

`workers/orbit-ingest/scripts/d1-query-stats.mjs` pulls `d1QueriesAdaptiveGroups` from the GraphQL
Analytics API, so a perf change can be diffed rather than screenshot-compared.
It prints rows read, count, read/call and **read/returned** (the scan detector)
and flags anything over 100×.

**Token scope resolved 2026-08-26 — the script works.** As of 2026-08-25
`CLOUDFLARE_ANALYTICS_TOKEN` in `.env` authenticated (a bad token 401s at the
HTTP layer) but returned `{code: "authz", "not authorized for that account"}` on
the `d1QueriesAdaptiveGroups` path, because it lacked **Account · Account
Analytics · Read**. That permission has since been added and the export now
returns data.

**What it immediately showed invalidates this log's conclusion — see
[docs/d1-read-model.md](../d1-read-model.md).** In short: `buildAnalytics()`'s
~16 unindexed `GROUP BY` tallies are ~84% of the read cost (1.42M of 1.68M rows
in one hour), roughly 5x everything fixed here. This session never saw it
because the dashboard was sorted by `Count`, which the paged group-bundle
queries dominate while `buildAnalytics()` hides near the bottom reading far
more. Sort by rows read, then by ratio — never by count.

Two API details found the hard way: the `sum` field is `queryDurationMs`, not
`queryDurationUs`, and `rowsReturned` **is** available — so the read/returned
ratio can be computed exactly rather than approximated by read/call.

## Deploy split worth remembering

This commit touches **two different deploy targets**:

| Path | Deploys via | Live when |
|---|---|---|
| `functions/api/` | Cloudflare Pages, on push | immediately |
| `workers/orbit-ingest/` | GitHub Actions, on **schedule** | next `gp` run |

So the decay-watch fix was live within a minute of the push, while the paging
fix sat in `main` unexecuted until an ingest run. A manual
`gh workflow run orbit-ingest -f job=gp` was used to confirm it the same night —
safe because the `gp` job makes exactly **one** upstream Space-Track call
([`ingest-gp.js:41`](../../workers/orbit-ingest/src/ingest-gp.js#L41)) against a
25/hour guard and a documented 300/hour ceiling.
