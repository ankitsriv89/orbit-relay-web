# Public Catalog Dashboard + Brief/News Plan

## Context

Two of the five nested `/spacetrack/` pages are underbuilt relative to the data that
already exists in D1:

- **`/spacetrack/analytics/`** is a four-panel CSS-bar page backed by one flat R2 read
  (`catalog/analytics.json`, rebuilt daily by `buildAnalytics` in
  [`derive.js:514`](../..//workers/orbit-ingest/src/derive.js)). It shows launches by
  decade, top launch sites (as raw codes like `AFETR` — no mapping exists anywhere, per
  AGENTS.md), debris families, and a country×decade matrix. No charting, no time series,
  no cohort or orbit-distribution views. The dataset is far richer than this page
  suggests.
- **`/spacetrack/brief/`** is a single "today" card backed by `brief/latest.json`
  (overwritten each daily ingest — **there is no archive** — so there is nothing
  "newsworthy" about it) plus three live drops: signal feed, reentry watch, boxscore. The
  AI narrative is facts-first and fact-checked, but it is one card with no history.

Special feature spec #19 ("Analytics Dashboard — statistics for objects, launches,
operators, orbit types *and trends*") is only partially met. Spec #18 (Historical growth)
ships for free from the data we already hold.

What this plan does NOT do: touch the `/admin/` dashboard, expose site traffic or ingest
operational data server, or add a charting dependency. Public analytics page = **catalog**
data; `/admin/` = **site** data (a visitor page half — page_views, ingest_runs — would
break `#privacy`'s plan-37 /about/ copy).

### Decisions already made (asked and answered before this doc was written)

1. **No charting library.** Repo rule in AGENTS.md ("no build step") plus `isolation of
   the "no dependencies" style. Charts are pure SVG/CSS generated by a small
   `public/shared/charts.js`, Node-testable in the existing orbit-ingest harness.
2. **Public data only.** No `page_views`, no `ingest_runs`, no admin internals on the
   public pages.
3. **Both pages are flat-read dashboards** — one R2 artifact read per page, refetched on
   an interval, degraded-report-as-stale, following `summary.js`'s discipline.
4. **Brief gets an archive** (`brief/YYYY-MM-DD.json`), manual/AI/absent narrative
   provenance, and auto-generated news rows from the `events` table.
5. **Reuse plan 36's admin auth** for the manual-brief override endpoint — no second
   password system.

## The dataset we are actually drawing from

Everything below is already in D1 today; nothing on this page requires new upstream
data.

- **`objects`** — full OMM/Gp mirror: `LAUNCH_DATE`, `DECAY_DATE`, `OBJECT_TYPE`,
  `COUNTRY_CODE`, `SITE`, `RCS_SIZE`, `SEMIMAJOR_AXIS`, `PERIOD`, `INCLINATION`,
  `EPOCH`, `regime`, `launch_year`, `debris_family`, `operator`, `first_seen`,
  `updated_at`. This single table powers nearly every analytics panel.
- **`boxscore`** — per-country orbital/decayed/payload/rocket-body/debris tallies,
  refreshed daily.
- **`events`** — the derived signal feed: `new_object`, `decay`, `reentry_predicted`,
  `satcat_change`. This is our **news feed** (Space-Track has no "what changed" endpoint;
  our ingest derives it).
- **`decay`** — reentry messages incl. 60-day predictions; also holds history.
- **`satcat`** — human-readable `SITE`/`LAUNCH` fields GP lacks (partial fix for the raw
  `SITE` problem — see 2.4).
- `api_calls`, `page_views`, `ingest_runs` — **admin-only**, listed to say explicitly
  what is *not* used here.

## Proposal A — `/spacetrack/analytics/` becomes the catalog dashboard

### A1. Extend the artifact, not the read path

`buildAnalytics` today writes `catalog/analytics.json` with only
`launches_by_decade`, `top_launch_sites`, `debris_families`, `country_by_decade`. Grow
it (still one GROUP BY per section, same ingest step, same day cadence) to:

```jsonc
{
  "generated_at": …,
  "tracked": …,
  "by_type": { "payload": …, "rocket_body": …, "debris": …, "unknown": … },
  "by_regime": { "leo": …, "meo": …, "geo": …, "heo": … },
  "launches_by_decade": […],
  "launches_by_year": […],                    // year-major for the recent era
  "cohort_on_orbit": [{ "decade": 1990, "launched": n, "still_on_orbit": n }],
  "top_launch_sites": [{ "site": "AFETR", "name": "Cape Canaveral SFS", "n": n }],
  "debris_families": […],
  "country_by_decade": { … },                // keep, add split by orbital/cool
  "rcs_sizes": { "SMALL": n, "MEDIUM": n, "LARGE": n, "UNKNOWN": n },
  "altitude_bins":  [{ "min": n, "max": n, "n": n }],   // over PERIA+APO / 2 per
  "inclination_bins": [{ "min": n, "max": n, "n": n }],
  "decays_by_month": [{ "month": "2026-01", "n": n }]     // last ~24 months, from events
}
```

Key `row` derivations:
- **cohort_on_orbit** — `GROUP BY (launch_year/10)*10`, `DECAY_DATE IS NULL` flag.
  "Of the things launched in the 1980s, how many are still up?" — interesting, free.
- **growth** (`launches_by_year` + a cumulative on-orbit count) — build cumulative
  "cumulative launched" over time; on-orbit-per-year is harder (needs decayed count by
  date), so keep growth as *launched-commulative* plus *still-on-orbit-today* per cohort,
  and label the distinction in the UI rather than pretending to a decay timeline.
- **altitude/inclination bins** — reuse the pure hating from plan 34 §2.2
  (`catalog/compute.js` heatmap binning) via a shared `bin()` helper.

`decays_by_trend` can move to its own endpoint if it needs faster refresh than daily;
default stays part of the daily artifact.

### A2. A new `/shared/charts.js` (SVG + CSS primitives) before any UI

Pure functions, no DOM framework, emits SVG nodes (SVG is static-friendly, no re-render
loop needed for once-a-day data):

- `bars(container, rows, {by, value, color, sorted})` → CSS `.st-bar` rows
  (reuse the existing `st-bar` classes).
- `stackedBars(rows…)` → for type×decade / country orbital-vs-decayed.
- `svgLine(points, {w,h, x, y, color})` → a small `<svg>` line/area path — used for
  growth and decay trends. SVG strings are fine here (fixed content, no user input), but
  prefer DOM creation per plan-33's `innerHTML` rule where reasonable.
- `svgHistogram(bins, {axis})` → alt/inclination distribution.

This is *the* place the repo's "pure math → Node-testable" discipline reaches the chart
layer. Unit-test `bin()`, the cumulative computation, cohort math in
`workers/orbit-ingest/test/` (the harness already reaches into `public/`). **Write the
bin/growth tests first and watch them go red against a naive grouping** — the CLAUDE.md
guardrail rule.

### A3. Dashboard layout

Replace the current 2×2 grid in `analytics/index.html` with registry-style sections
(modeled on plan 36's `registry.js`, but static HTML sections — no accordion needed on a
scrolling page):

1. **KPI strip** — tracked / payloads / debris / regime split / last elset from the
   artifact; `stale: true` becomes a visible hint.
2. **Growth** — area line (launch-accumulated) + on-orbit today marker.
3. **Cohort survival** — stacked horizontal bars by decade (in-orbit vs decayed).
4. **Orbit distribution** — two histograms (altitude, inclination). `approx` labels.
5. **Type & RCS** — type split + RCS-size bars.
6. **Launch sites** — top 12 ranked; now with human-readable `name` when mapped.
7. **Debris families / country×decade matrix** — keep the existing panels (and its
   `country_by_decade.da` non-reversal of the DATA matrix stays), wrapped to fit.
8. Degraded-mode behavior: if the artifact's Stile = true, render the sections that have
   data and say "counted live from D1 — R2 artifact not built yet" instead of silently
   showing partial bars. Keep the per-section hint pattern the page already uses.

### A4. `SITE` code → name (fix the unreadable launch-site panel)

From AGENTS.md: "objects.SITE is a raw code (`AFETR`) with no human-readable mapping
anywhere in the repo, despite `orbit.sql:98-99` implying SATCAT carries one." The
quickest correct source is `satcat.LAUNCH` (seed map once at ingest into a small
`launch_sites` name), or ship a static `public/data/launch-sites.json`. Build the map in
`buildAnalytics` from `satcat` `(SITE, LAUNCH)` pairs so the artifact ships names
alongside codes. Trumping list: `${SITE} — ${name}`.

## 2 — `/spacetrack/brief/` becomes briefs + news archive

### B1. Archive the brief (the enabler)

Today `brief/latest.json` is the only R2 keyspace entry. Change `buildBrief` to write
**both**:

- `brief/latest.json` (unchanged read path — `/api/brief` stays as-is, old semantics).
- `brief/<YYYY-MM-DD>.json` (the same card, keyed by the day it narrates).

And write `brief/index.json` (or serve a small `/api/brief/index` listing
date + `signature` headline + `narrative_status`) so the frontend can render an archive
selector without listing R2 keys on every load.

`/api/brief` gains `?date=YYYY-MM-DD` (default latest), `?index` → card records. All
shaped with `withCitation`, no D1 fallback on reads by design — the insert side is the
only write path, and it happens once a day at ingest (the same "no inference/regression
on read path" rationale `brief.js` documents today).

### B2. Narrative provenance

The card already carries `narrative_status`. Extend it to record **who wrote the prose**:

- `narrative_source: 'ai' | 'manual' | 'none'`.
  - `'ai'` — status is `ok` after the check-gate.
  - `'none'` — `disabled` / `skipped` / failed gate.
  - `'manual'` — authored via `/api/admin/brief` (below), which overrides whatever the
    AI produced for that day.

`checkNarrative()` (the grounding gate) applies to **AI** prose only; manual text is
author-signed and does not go through it. The public page shows the badge line exactly as
today, plus — only when `manual` — `“Edited"` vs `“AI-generated"` so the reader knows
which voice they're reading.

### B3. Manual-brief endpoint (`/api/admin/brief`)

Reuse plan 36's auth (`_middleware.js`, HMAC cookie), never a new password. `POST`
with `{ date?: 'YYYY-MM-DD', narrative, note? }`:

- Writes/overwrites `brief/<date>.json`'s `narrative` (the card's facts stay — arm facts
  are corrected by number asserted, not by hand).
- Sets `narrative_source: 'manual'`.
- **Rejects** any `'manual'` narrative containing a forbidden collision/conjunction
  phrase — the editorial rule is a *legal* one, not a stylistic one (see
  `brief.js`'s `FORBIDDEN`). Manual text gets the same language block that AI text does;
  it just skips the number-gate.

This slots into admin as `panels/brief-editor.js` — one new file + one line in
`registry.js`, exactly plan 36's extension contract.

### B4. Auto news sections (the "news" part)

Build the news feed entirely off the `events` table (already derived, already on R2).
The desktop HTML assembles:

- **Today / Recent** — signal-feed rows grouped by day. All four kinds already exist:
  `new_object` (≈ "new launch/catalog entry", render with type + country),
  `decay`, `reentry_predicted` (badge "imminent" when ≤7 days), `satcat_change`.
- **"Recent launches" proxy** — filter `new_object` events for `OBJECT_TYPE = payload`;
  title renders `SATNAME (designator)`. This is the closest to a launch list the client
  I deal put out; mark it as *catalog entry*, not a launch-authoritative source.
- **Manual features / blog-style items** — an optional editor-only field on the archive
  card (`featured: true`) that surfaces a curated "note from the operator" above the
  auto feed. v2; one flag.

**Constraints locked in:
- `FORBIDDEN` collision language stays enforced for all narrative text, AI and manual.
- AI prose is build-only-per-day, fact-checked to the number.
- Nothing here tries to be a news-author — it renders generated events + posted briefs.

### B5. Publication ordering

A `brief` `index` update must be written **after** the day-card, and the write itself
must never open the ingest. `recordRun` pattern already says 'losing a log row beats
losing an ingest' — same heatmap for the index: failure to write `index` journals a
`console.warn` and leaves the previous index (dates shift, no false gap).

## Cross-cutting

### C1. Reuse of plan 36's engineering (by analogy, not shared state)

- **Panel isolation**: a single section render failure must not blank the page
  (`APIs load()`/`render` errors caught per-panel, `.st-hint` on failure). Keep the
  random — a dashboard is only as good as the one thing that's broken.
- **Mobile**: dashboards carry wide histogram/matrix content — 
  `overflow-x: auto` on those sections, no horizontal page scroll, ≥44px touch targets,
  collapsed on 390px viewport first, then tables. Add mobile assertions in
  `tests/e2e/test_mobile_responsive.py` (or a `test_dashboard_mobile.py` sibling),
  matching plan 36's contract — assert `scrollWidth <= innerWidth`.
- **Cite** — every endpoint response keeps `withCitation` (XP Framework citation on
  thing that carries D1 data). It's lavish. Don't add a captor: new analytics sections
  are served through `artifactOrDb`, so citation shipping is inherited.

### C2. plan 34 §2.2 tie-in

The altitude/inclination binning and the growth aggregation are same-class 
as the catalog heatmap math: extract `bin()` etc. into a `public/shared/bin.js` or
`catalog/compute.js` module that both globe and dashboard import. Keeps one grouping,
one test.

### C3. plan 37 wiki tie-in

Once the dashboard adds `cohort`, `altitude bins`, "catalog entry vs launch" to the 
phrase precision, the wiki glossary gets one-line additions (`derive`, `cumulative`,
`on-orbit vs launched`, `launch site name`). Keep in step with the wiki, don't fork.

### C4. Attribution

Analytics/brief pages already carry the Space-Track citation string in footer;
the `X-Data 源` header is preserved on the new endpoints via `withCitation`. Nothing here
adds a second data provider (space weather is out of scope — see Open decisions).

## Build sequence

Ordering forced by the same resolve/offline-test gates as plan 34–36: features landing
before their referrers.

1. **Artifact + indices** — extend `buildAnalytics` (rows in the table under A1),
   add `launch_sites` map, write `brief/YYYY-MM-DD.json` + `brief/index.json` in
   `buildBrief`. These are ingest-only; the running site is unaffected until a step below
   consumes them. Check `test/schema.test.mjs` interplay if you touch it —
   `brief.test.mjs` covers the card build.
2. **Pure math module (`charts.js` + shared `bin`/`growth` helpers)** with the first
   frontend unit tests in the existing harness — State Red before the UI. This is the
   glass door of the whole dashboard.
3. **`/api/brief?date=` + `/api/brief/index`** endpoints via `artifactOrDb`; `?date=`
   reads an R2 key directly; `index` reads `brief/index.json`. Tests: `brief-index.test.mjs`
   (archive lists older days, latest stays current, missing day = `available:false`,
   `narrative_source` round-trips 'manual').
4. **Rebuild `/analytics/`** with sections over the ossified artifact (charts.js), the
   site-name codes, and the stale reporting. Then update the nav/mobile drawer? No nav
   change — route names stay.
5. **Rebuild `/brief/`** (archive selector — day list from `/api/brief/index`, the news
   groups B4, the provenance badges).
6. **Admin brief editor** — `panels/brief-editor.js` + endpoint, final; it touches the
   auth path that must exist first (plan 36).
7. `npm test` green; the `resolve.mjs` will enforce every new intra-page ref; mobile
   assertions per C1.

### Out of scope (flag for future plan)

- **Site traffic / visitors** on public pages (that's `/admin/`, plan 36).
- **Space weather** (plan 34 §3.4) — second provider, second citation; it'd be its own
  dashboard section, not this one.
- **Ground-station / launch site DB** beyond the name map above.
- **Subscriptions / feeds / push** (notifications) — spec #16-adjacent, needs retention
  and serialization.

## Risks

| Risk | Severity | Mitigation |
|---|---|---|
| A dashboard borks the static CSS bar page | Medium | Keep .renderer table unstyled/ overflow container; run the catalog mobile suites. |
| `buildAnalytics` no longer matches `functions/api/analytics.js`'s assumptions | Medium | The fallback `artifactOrDb` reduced-form response stays unchanged; UI must handle "partial artifact" (stale flag). |
| The incompleteness of "on orbit over time" — growth is an approximation | Low | UI axes say "cumulative catalog entries" and "still on orbit today"; never claim a true historical on-orbit profile. |
| Archive write failing takes down ingest | Medium | Same try/catch discipline as `recordRun`; write through `put` and only `warn`. |
| Manual brief breaking the AI gate / appearing "AI" when it isn't | Medium | `narrative_source` on every card, asserted in tests, badge in UI. |
| `bin.js`/`charts.js` growing into a wiki of UI state | Low | keep them pure; the DOM-owning layer stays in each page's `js/fetch`.

## Open decisions

1. **Year vs decade axis on growth** — recommend year-major for 2000+, decade for the
   historical matrix (matches how the data reads).
2. **`/api/brief/index` max rows** — it'll keep ~730 daily records; return the last
   60 days + a `total`, lazy so the client never loads the whole history (Photono).
3. **Where code lives for charts** — decided `public/shared/charts.js`; register in a
   `/admin/registry`-style page registry? Decide when the dashboard has five — analytics
   2 may as well.
4. **Manual-brief editor free-form vs a dropdown** — v1: single text field + date +
   note landed; the "featured note" is v2.
